# #159 — "Resend" on a bid request that was never sent

## What was measured (S108, verify it)
- `estimate_sub_bid_requests.sent_at` has `DEFAULT now()`, so a request is "sent" the moment it is
  created.
- `bidding-tab.tsx:538` renders `Resend` when `sent_at` is set, so the **Send branch is dead code**
  and the first real send is a button labelled Resend. Josh hit exactly this on production.
- S107's B3b already made the send route stamp `sent_at` on success. **The default is the defect.**
- The creation dialog shows only the link — **there is no Send in it.**

## RULED
- The fix is `DROP DEFAULT` so `sent_at` means sent.
- ⚠️ **The creation dialog must offer Send**, not only a copyable link. Josh should not have to find
  a second control to do the obvious thing.

**FILL-159.1** — Every reader of `sent_at`: the label, the expiry, the "resend reuses the same
token" rule, any report or list. State what each does when it becomes NULL.

**FILL-159.2** — ⚠️ **The back-fill question.** Existing rows carry a `sent_at` that may mean
created, not sent. Propose how to tell them apart — `email_logs` is the instrument, and S108 flagged
its retention as unverified. **Count the affected rows on PRODUCTION before proposing anything;
give Josh the query.**

**ASK-159.A** — On FILL-159.2: back-fill from `email_logs`, leave existing rows alone, or something
else.

## What was measured
Deleting a profile marks `profiles.is_deleted` and leaves the matching `company_members` row active.
The Team page hides the person; the project **Assign a member** dropdown still lists them. Josh hit
this on production — two "Juan Cardona" rows, one on a deleted test profile. Cleaned by hand on
2026-09-22 (`company_members` `55b55c4a-48f9-4f05-b40c-5d3e9ce28f8a`); a production sweep found no
others.

## RULED
- ⚠️ **The fix belongs in the DATABASE, not in each delete path.** The two tables must agree by
  construction — every future delete path inherits it, and none can forget.

**FILL-160.1** — Every path that soft-deletes a profile, and every path that soft-deletes a member.
⚠️ **Both directions:** does removing a member leave an orphaned profile?

**FILL-160.2** — What else keys on `company_members` and would change behaviour when a row becomes
deleted: assignments, schedule, punch items, time clock, chat, notifications. ⚠️ **A member with
history must not lose it** — state what happens to past rows.

**FILL-160.3** — Production and rebuild-test counts of members whose profile is deleted, and
profiles whose member is deleted. Give Josh the queries; he runs them.

**ASK-160.A** — On FILL-160.2: does a ghost found by the sweep get cleaned automatically, or listed
for Josh to decide?

# #162 — No way for a user to change their own password

## What was measured
`/reset-password` **already changes a password with no email and no recovery token** — a signed-in
user who types the URL succeeds today. What is missing is any link to it from inside the app; both
real entry points go through email, which is what failed Josh. It is **not** on
`/dashboard/settings`, which is Owner/Admin-only and unreachable by the foreman and crew who hit
this.

## RULED
- Add the affordance where any role can reach it.
- ⚠️ **Three real staff accounts on production share one password** (`worthproperties`, set by hand
  on 2026-09-22). This is the fix that lets them off it.

**FILL-162.1** — Which pages every role can reach, and where the control belongs for all of them.

**FILL-162.2** — ⚠️ **The page asks for NO current password.** Anyone with a live session — an
unlocked phone left on a jobsite — can change that account's password. State exactly what the page
does today.

**ASK-162.A** — On FILL-162.2: require the current password before changing it? That is a security
change to a live page, so it is Josh's call, not an implementation detail.

# #163 — Only the row's text is clickable

## RULED [Josh]
- ⚠️ **The whole row is the click target wherever rows of items are listed** — files, contacts,
  everything — and the row opens the item.

## What was measured (S108 — this changes the shape of the work)
- `components/list-screen/list-screen.tsx` **renders no row.** It shares the header, search, metrics,
  alert and chips, and refuses to share the table on purpose: *"a generic table component would be a
  framework, not a pattern."*
- **Nine adopters**, not six. Contacts and subs already do whole-row with full keyboard support
  under a prior ruling. Five more are whole-row but **mouse-only**. `ListRowLink` on mobile already
  solves this, with both traps documented.

**FILL-163.1** — The nine adopters and, for each: whole-row or text-only, keyboard-reachable or not.
A table.

**FILL-163.2** — ⚠️ **Three traps, each a real regression if missed:**
1. a row containing its own buttons (delete, Remove, Send) must not fire the row action;
2. the S108 line-items **drag handle** must still drag — ⚠️ **clicking it to focus is the documented
   KEYBOARD reorder path, so a card-level click handler breaks the very affordance this is meant to
   improve;**
3. the row must be announced as a link or button, not a bare `div` with an `onClick`.

**ASK-163.A** — ⚠️ **The shape of the fix, and it is Josh's call:** extract a shared row primitive
(one place, nine migrations to it, a framework risk the list-screen author deliberately refused), or
apply `ListRowLink`'s pattern per screen (nine edits, no new abstraction, drift possible later).
**Do not choose this yourself.**

# #159 — "Resend" on a bid request that was never sent

## What was measured (S108, verify it)
- `estimate_sub_bid_requests.sent_at` has `DEFAULT now()`, so a request is "sent" the moment it is
  created.
- `bidding-tab.tsx:538` renders `Resend` when `sent_at` is set, so the **Send branch is dead code**
  and the first real send is a button labelled Resend. Josh hit exactly this on production.
- S107's B3b already made the send route stamp `sent_at` on success. **The default is the defect.**
- The creation dialog shows only the link — **there is no Send in it.**

## RULED
- The fix is `DROP DEFAULT` so `sent_at` means sent.
- ⚠️ **The creation dialog must offer Send**, not only a copyable link. Josh should not have to find
  a second control to do the obvious thing.

# #160 — Removing a team member leaves a ghost

## What was measured
Deleting a profile marks `profiles.is_deleted` and leaves the matching `company_members` row active.
The Team page hides the person; the project **Assign a member** dropdown still lists them. Josh hit
this on production — two "Juan Cardona" rows, one on a deleted test profile. Cleaned by hand on
2026-09-22 (`company_members` `55b55c4a-48f9-4f05-b40c-5d3e9ce28f8a`); a production sweep found no
others.

## RULED
- ⚠️ **The fix belongs in the DATABASE, not in each delete path.** The two tables must agree by
  construction — every future delete path inherits it, and none can forget.

**Entry, quoted (`TECH_DEBT.md:132`):** _"removing a team member leaves a ghost in
`company_members`; the two tables do not agree."_ … _"**Fix shape:** an `AFTER UPDATE` trigger on
`profiles` that propagates `is_deleted`/`deleted_at` to the matching `company_members` row"_ …
_"(a) **It must propagate the restore as well as the delete** … (b) **`company_members` rows with
`profile_id IS NULL` are legitimate and must be left alone**."_

**FILL-160.1** — Every path that soft-deletes a profile, and every path that soft-deletes a member.
⚠️ **Both directions:** does removing a member leave an orphaned profile?

> **FILLED.** **Profile soft-delete:** exactly one app path, `softDeleteTeamMember()`
> (`lib/services/team.ts:118-134`, update `:126`, then an 876000h auth ban), called only from
> `dashboard/team/[id]/actions.ts:88`. **Profile restore:** **none** anywhere — app, SQL, scripts.
> **Profile hard delete:** only the trial purge (`lib/trial/deletion.ts:430`), whole company.
>
> ⚠️ **YES — THE OTHER DIRECTION EXISTS, AND THE RULED TRIGGER DOES NOT COVER IT.**
> `/m/team/[memberId]/edit/team-edit-form.tsx:125-134` writes `is_deleted: active === 'inactive'`
> straight to `company_members` via `updateMember()` (`members-client.ts:92`), Owner/Admin under
> `company_members_update_authorized`. It never touches `profiles` and never bans. **Result: a
> deleted member row over a live profile that can still sign in** — the reverse ghost. That form
> also restores (inactive → active). → **ASK-160.B.**
>
> ⚠️ **And that form sends `is_deleted` on EVERY save, and writes the profile in the same submit**
> (`updateMemberProfile`, `:136`). So a trigger that copies `is_deleted` on any profile UPDATE
> would **silently undo a `/m` deactivation**. **The trigger must fire only on
> `NEW.is_deleted IS DISTINCT FROM OLD.is_deleted`.** Not a choice — a build constraint.
>
> ⚠️ **Constraint (b) is incomplete: linked SUB rows.** `subcontractors_create_member` inserts a
> member with `profile_id NULL, member_type 'subcontractor'`; `handle_new_user()` then runs
> `UPDATE company_members SET profile_id = <new profile> WHERE id = invitation.member_id AND
> profile_id IS NULL` — **an invited sub user's profile is linked to the sub DIRECTORY's member
> row.** A trigger keyed on `profile_id` would soft-delete that directory row when the sub's login
> is removed: the sub leaves every picker while its `subcontractors` row stays live. Rebuild-test
> has 1 such row. Precedent: `sync_member_display_name()` excludes `member_type <> 'subcontractor'`
> for this exact reason (`20261100000000_sync_member_display_name.sql:22, :41, :69`). → **ASK-160.C.**
>
> **Sibling, same shape, out of scope:** `deleteSubcontractor()`/`restoreSubcontractor()`
> (`subcontractors-client.ts:46-86`) change only `subcontractors`; the member row stays live.
>
> **Schema facts the trigger relies on (rebuild-test):** `idx_company_members_profile_id` is
> `UNIQUE (profile_id) WHERE profile_id IS NOT NULL` — **1:1**, and it does not exclude deleted
> rows, so a restore cannot collide. No DELETE policy on `company_members`. Existing triggers on
> `profiles`: `profiles_create_member` (AFTER INSERT; skips client/subcontractor),
> `profiles_self_column_scope` (already stops a user writing their own `is_deleted`),
> `profiles_sync_member_display_name` (AFTER UPDATE), `profiles_updated_at`.
